::: goal
You will use the learned merges to turn any text into token ids (`encode`) and back into the same text (`decode`). Encoding applies the merges in the order they were learned.
:::

::: notation
| Symbol | Meaning |
| --- | --- |
| merge $k$ | the $k$-th learned pair $(a, b)$; it creates the id $256 + k$ |
| rank | the order in which a merge was learned; a lower rank means it was learned earlier |
| token bytes | the bytes a token stands for: `vocab[256 + k] = vocab[a] + vocab[b]` |
| compression | bytes of text divided by the number of tokens |
:::

::: numpy
### A dictionary from pairs to new ids

```python
merges = [(97, 97), (256, 97)]
rank = {pair: 256 + i for i, pair in enumerate(merges)}
print(rank)                              # {(97, 97): 256, (256, 97): 257}
print(rank.get((1, 2), float("inf")))    # inf   a pair that was never learned
```

`dict.get(key, default)` returns `default` when the key is missing. `float("inf")` is larger than every number, so `min` never picks an unknown pair.

### Joining bytes and decoding them

```python
vocab = [bytes([i]) for i in range(256)]   # the 256 single bytes
print(b"".join([vocab[104], vocab[105]]))  # b'hi'
print(b"\xec\xb4".decode("utf-8", errors="replace"))   # �   half of a Korean character
```

`errors="replace"` turns bytes that don't form a whole character into `�` instead of crashing. That can happen when a sample stops in the middle of a multi-byte character.

### A cache

A dictionary that remembers results avoids repeating work:

```python
cache = {}
if chunk not in cache:
    cache[chunk] = ...      # compute once
ids = cache[chunk]          # reuse every other time
```
:::

::: concept
### Encoding one chunk

Start from the chunk's bytes. Then, again and again: look at all neighbouring pairs, and apply the learned merge with the **lowest rank** among them, everywhere in the chunk. Stop when no pair in the chunk is a learned merge.

Why the lowest rank? During training, merge 0 was applied to the whole text before merge 1 even existed, merge 1 before merge 2, and so on. Later merges were learned on text that already contained the earlier ones. So encoding must replay them in the same order.

**Example** with merges $[(97, 97), (256, 97)]$, that is, `aa` → 256, then (256, `a`) → 257:

| text | bytes | step 1 (lowest rank present) | step 2 | result |
| --- | --- | --- | --- | --- |
| `aaa` | 97 97 97 | `aa` (rank 0): 256 97 | (256, 97) (rank 1): 257 | [257] |
| `aaaa` | 97 97 97 97 | `aa` (rank 0): 256 256 | no learned pair | [256, 256] |

Each step merges **all** occurrences of the chosen pair, left to right, with `merge_pair` from s3-l01.

### Encoding a whole text

Split the text with `pretokenize`, encode each chunk, and join the ids. Stories repeat the same words constantly, so remember each chunk's ids in a dictionary (a cache) and encode each distinct chunk only once. In 1 MB of TinyStories there are about 245,000 chunks, but only 4,670 different ones.

### Decoding

Each token stands for a fixed sequence of bytes. Build that table once (`build_vocab`, given): the 256 single bytes, then for each merge $(a, b)$ the bytes of $a$ followed by the bytes of $b$. To decode, join the bytes of all ids and decode them as UTF-8.

There is no "unknown token" problem: every id has bytes, and every text can be encoded. One subtle point: a single token can hold part of a multi-byte character, because merges work on bytes. Text generated by a model can therefore end in the middle of a character. `errors="replace"` shows such a piece as `�` instead of crashing.

### How much shorter does the text get?

With 4,096 tokens learned on TinyStories, the 100 MB training text becomes **26.6 million** tokens: about **3.94** characters per token. A model with $T = 256$ positions therefore sees about $256 \times 3.94 \approx 1{,}000$ characters of story at once, instead of 256 with characters as tokens.
:::

::: think
Q: Why must encoding apply the merges by rank instead of, say, always merging the most frequent pair in the new text?
A: The merges only make sense in their learned order: merge 257 = (256, 97) assumes merge 256 already happened. Using a different order on new text could produce different tokens for the same word than during training, and the model would see sequences it was never trained on.
:::

::: think
Q: A model generates the ids of a story, and you decode them. Why might the last character come out as `�`?
A: Tokens are byte sequences. If generation stops after a token that holds only the first bytes of a multi-byte character (a curly quote or an emoji), the bytes are incomplete. `errors="replace"` shows them as `�`.
:::

::: hint level=1
`encode`: make a dictionary from each merged pair to its new id; for each chunk, start from its bytes and keep merging the learned pair with the smallest new id until none is left; cache the result. `decode`: join the bytes of the ids and decode.
:::

::: hint level=2
`rank = {pair: 256 + i for i, pair in enumerate(merges)}`. Inside a `while len(ids) >= 2` loop: `best = min(set(zip(ids, ids[1:])), key=lambda p: rank.get(p, float("inf")))`; stop if `best not in rank`; else `ids = merge_pair(ids, best, rank[best])`. For `decode`: `vocab = build_vocab(merges)`, then `b"".join(vocab[int(i)] for i in ids).decode("utf-8", errors="replace")`.
:::

::: hint level=3
```pseudo
encode(text, merges):
    rank ← {pair: its new id} for every merge
    out ← [];  cache ← {}
    for each chunk of pretokenize(text):
        if chunk is not in cache:
            ids ← the chunk's UTF-8 bytes
            repeat:
                best ← the neighbouring pair with the smallest rank (unknown pairs: infinity)
                if best has no rank: stop
                ids ← merge_pair(ids, best, rank[best])
            cache[chunk] ← ids
        add cache[chunk] to out
    return out
```

::: recap
- Encoding replays the merges in learned order: always the lowest-rank pair first.
- A cache of chunks makes encoding large texts fast.
- Decoding joins token bytes and decodes UTF-8; every id has bytes, so nothing is ever unknown.
:::
